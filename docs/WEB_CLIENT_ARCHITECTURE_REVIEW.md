# Web / Tauri Client 共用优先审查与整体调整计划

> 审查日期：2026-09-01
> 本文是现状审查和后续改造计划，不代表所有候选改造已获准实施。

## 1. 长期决策原则

Web 与 Tauri 的业务效果一致时，直接开发和维护 `web/` 中的一套 Vue 页面，由 `client/src/main.ts` 复用，不建立桌面专用页面、状态或 API 分支。

只有 Tauri/Rust 在安全、操作系统集成、可靠性或性能上存在明确且可验证的收益时，才考虑平台适配。实施前必须向维护者说明：

1. 当前 Web 实现的具体限制及可复现证据；
2. 原生方案带来的用户收益；
3. Rust/Tauri 代码、权限、签名和跨平台维护成本；
4. Web 端保留的降级体验；
5. Windows、macOS 和浏览器分别需要的验收范围。

没有明显差异或证据不足时，结论固定为继续共用 Web 实现。

## 2. 当前实现审查

| 能力 | 当前边界 | 审查结论 |
| --- | --- | --- |
| 业务页面与权限显示 | `client` 直接加载 `web/src/main.ts` | 保持共用；客户、仓库、任务单、模具等不得复制桌面页面。 |
| API 与认证续期 | Vue 共用请求层；浏览器用同源 Fetch，Tauri 注入插件 HTTP | 差异合理地封装在传输适配器，业务组件不感知平台。 |
| 客户 Excel 导入 | 共用 HTML 文件选择、`FormData`、预览和确认 UI | `.xls/.xlsx` 选择与上传效果一致，当前没有引入 Rust 文件选择的必要。 |
| 客户 Excel 导出预览 | 共用后端分页 JSON 和工作表式 Vue 表格 | 效果一致，应继续共用；浏览器不解析真实 XLSX 是正确边界。 |
| XLSX 文件下载 | 共用受保护 Blob 下载和浏览器/WebView 下载接管 | 代码可共用，但 Windows/macOS Tauri 的保存位置、失败反馈和大文件行为尚缺真实验收，不能仅凭构建判定完全等效。 |
| 请求超时 | Web 沿用浏览器；Tauri 插件传输有显式超时 | 已把客户导入/导出归入 60 秒文件请求，这是传输层差异，不需要页面分叉。 |
| 服务地址 | Web 使用同源；Tauri 保存内网服务地址并测试连接 | 属于桌面部署必要差异，继续放在桥接层和共用设置界面。 |
| 客户端自动更新 | Vue 展示状态，Rust 计算 EXE 哈希、验签、下载、安装和回滚 | 明显依赖本机程序和签名安全，必须保留为 Tauri/Rust 专属能力。 |
| 服务端升级包下载 | Go 同源接口完成签名和包校验，Vue 发起受保护下载 | 校验必须留在 Go；是否用原生保存仅按实际 WebView 下载问题另行决策。 |

本次客户模块符合共用优先原则：四个客户组件全部位于 `web/src/components/pages/`，Web 和 Tauri 使用同一状态、权限、导入、预览和下载流程；平台差异只存在于既有 HTTP 传输适配器。

## 3. 已发现的整体问题

### P1：交付前必须验证

- Tauri 的 Blob 下载是否在目标 Windows 10/11 和 macOS 上稳定弹出/保存、保留正确文件名并反馈失败，尚无真实窗口证据。
- 客户 `.xls/.xlsx` 上传、50/100 行预览分页及下载需要分别在真实 Web 和 Tauri 登录态验证；静态构建不能替代。
- 权限变化后的 `403`、令牌续期、上传超时和下载失败需要确认共用页面能保留上下文，不出现平台独有死状态。

### P2：后续可维护性

- `useWorkspaceController.ts` 仍集中承担导航、缓存和大量跨模块状态；专用页面已开始拆出，但共享控制器仍是变更冲突热点。
- Web 与 Client 使用不同的 Vite 主版本并各自生成组件声明，虽能构建，升级时仍需双构建验证。
- 文件能力目前只有共用 `downloadApiFile` 函数，没有显式“下载能力”接口；一旦确认需要原生保存，容易在业务组件内直接判断平台。
- 大型前端主包仍有超过 500 kB 的构建警告，客户页面继续静态合入主包；这是加载性能问题，不是启用平台分叉的理由。

## 4. 分阶段调整计划

### 阶段 A：建立边界和验收基线

1. 把本原则加入 Web/Client 维护文档和评审清单。
2. 建立 Web 与 Tauri 共用业务验收表：同一账号、同一数据、同一操作，分别记录页面结果、API 结果和平台反馈。
3. 对上传、下载、打印、扫码、通知、剪贴板和本机文件访问建立“共用 Web 是否足够”的证据项；没有失败证据不启动 Rust 改造。

### 阶段 B：收敛共享架构

1. 继续把客户、部门、员工等独立业务状态从 `useWorkspaceController.ts` 拆到模块 composable，但导航和会话保持共用。
2. 把客户选择统一封装为资料选项服务，仓库、任务单、模具只消费 `CustomerProfile.ID`，不各自解析客户列表。
3. 为文件下载定义平台无关的 `FileDownloadCapability` 接口；默认实现仍是 Blob 下载。此步骤只建立边界，不自动增加 Rust 命令。
4. 评估页面级动态加载降低首包体积；Web 和 Tauri继续使用同一拆包方案。

### 阶段 C：仅在证据成立后评估原生能力

首个候选是“导出到用户指定位置”：若真实 Tauri 验证证明 Blob 下载无法稳定保存、无法反馈路径或大文件失败不可恢复，再向维护者提供 Rust 保存对话框方案。方案应包含文件名、覆盖确认、写入临时文件后原子替换、权限/CSP、取消与失败状态，并保留 Web Blob 下载。未经确认不实施。

打印、扫码、桌面通知、离线缓存等能力同样按单项业务需求审查，不能以“桌面端优先”为理由预先建设。

## 5. 架构改动验收门槛

- 业务组件中不直接出现新的 `isDesktop` 分支；平台选择只发生在能力适配层。
- 同一业务 API、DTO、权限和错误文案在 Web/Tauri 只有一个来源。
- 原生能力必须有 Web 降级实现和 Windows/macOS 独立测试；Web 构建、Client 构建与 `cargo check --locked` 同时通过。
- UI 审查需覆盖 1280、920、768、600、390 和 320px；Tauri 还需真实窗口、文件对话框/下载和内网传输检查。
- 产品终审必须确认原生收益高于新增 Rust、安全权限、签名和发布维护成本；否则保持共用 Web。
