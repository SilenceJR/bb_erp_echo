## 1. 当前结论

Go 后端核心业务已经形成可运行的模块化单体：Echo HTTP 服务、SQLite WAL、JWT/Casbin 认证授权、员工与部门成员、双重责任审计、基础资料、库存、模具、任务单、统计、受保护图片和客户端更新服务均已接入应用装配与 API 文档。

当前不能称为“生产验收完成”。员工、部门、业务操作人责任链已经实现并有定向测试；完整 Go 测试、静态检查和真实登录运行态结论以本节验证记录为准。GitHub Actions 的 Go job 仍是远端正式验证入口。

`0.0.2`、`0.0.3` 和 `0.0.4` 均因 Gitee 大附件 0 字节响应超时未形成完整正式发布，源码标签保持原提交不变。`0.0.5` 已建立正式完整更新基线，`0.0.6` 已发布七个附件；`0.0.7` 已修复公钥部署边界和服务端升级回滚，`0.0.8` 已形成从 0.0.7 出发的签名差分。两版均通过正式附件、匿名 SHA-256、签名和稳定 manifest 技术验收，不新增后端业务 API。Windows 10/11 用户升级尚未验收完成，仍保持“发布环境闭环：进行中”。

首次 `v0.0.2` Windows CI 暴露 Tauri 更新命令在 Windows 专属编译路径中的 Rust `Result` 错误类型推断问题，已补充显式类型并通过后续 Windows 构建；后续几版暴露 Gitee 大附件长时间无响应问题。当前在 multipart 表单认证基础上增加附件状态查询、断点恢复、慢速上传容忍和无进度中止，并通过 `0.0.5` 重新验证。上述问题不改变 API 或更新流程设计。

## 3. 已完成内容

### 3.1 服务基础设施

- cmd/server 已负责装配配置、数据库、权限服务、业务 Handler、更新服务、Swagger 和 Web 静态文件。
- /health 与 /ready 已提供；服务启动时执行数据库连接、自动迁移、默认组织/角色/权限/管理员初始化。
- SQLite 使用 WAL、外键和 busy_timeout；连接池限制为单写连接，符合当前单机内网定位。
- 配置支持默认值和 BB_ERP_ 环境变量覆盖；JWT 使用系统内部密钥，管理员先使用默认密码登录并在系统内修改；更新签名公钥仍由发布配置提供。

### 3.2 认证、权限与审计

- 登录返回 JWT、refresh token 和当前账号信息；受保护 API 通过 Bearer Token 校验账号状态，refresh token 只保存 SHA-256 摘要并在成功续期后轮换。
- `/api/v1/auth/refresh` 支持活跃会话自动续期，`/api/v1/auth/logout` 撤销 refresh token；修改密码会在同一事务中撤销该账号全部 refresh 会话。
- Casbin 权限以 API object/action 表达，当前 action 为 read/write；中间件同时校验组织和部门数据范围。
- 部门终端操作员默认同时拥有 `warehouse:read` 与任务读写权限，才能搜索生产单产品并读取库存；若无仓库查看权限，不应授予任务单权限。
- cost:view 独立控制采购单价、平均成本、库存金额和统计金额，后端响应会主动裁剪无权限字段。
- 写操作审计记录账号类型、组织、账号部门、终端、所选操作员工与操作部门快照、请求 ID、路径、状态和结果；历史空值不伪造员工。操作员工属于当前账号对现场责任人的申报，不替代 PIN、刷卡或二次认证，因此追责必须同时查看登录账号和终端。

### 3.3 业务闭环

- 基础资料已覆盖部门、员工、客户编码/客户资料、供应商、仓库、库位、物料和产品。客户联系人与联系电话属于单条客户资料，不再使用独立联系人模块；客户资料采用物理删除并阻止删除已被历史业务记录引用的资料。员工可属于多个部门，年龄按上海当前日期实时计算；员工和部门均启停保留历史。
- 任务单和仓库/库存写入统一校验账号当前部门、部门状态、员工状态、组织及成员关系；缺字段、越权和关系失效分别按 400、403、409 拒绝且不产生业务写入。
- 库存数量使用四位定点整数，金额和单价使用分；转换和加权平均成本计算在后端完成，避免浮点误差。
- 库存单据支持草稿、过账和冲销；Idempotency-Key 用于避免重复创建同一业务请求。
- 生产单创建必须关联启用仓库产品；服务端覆盖客户端名称和单位，保留产品 ID 与创建时快照。生产单内临时建档创建启用产品但不写库存余额或流水；`workorder:temporary-product:write` 默认仅超级管理员拥有。
- 仓库物品详情按默认仓库所有库位汇总库存数量和成本，保持与仓库产品列表一致；无成本权限时继续裁剪成本字段。
- 模具操作必须经过合法状态转换并记录履历；任务单主状态由办公室流程控制，部门只操作自己的子任务状态。
- 图片文件按业务 owner 继承权限，路径经过安全校验，上传文件名不直接作为存储文件名；创建接口以重复 `file` 字段接收单图/多图，批量保存失败会清理本批次文件并回滚记录。

### 3.4 更新与发布支撑

- 服务端保留旧版客户端 ZIP 接口，兼容已有客户端。
- v2 更新清单在服务端验签后才进入内容寻址缓存；差分资源失败时降级使用完整包，不覆盖上一份可用状态。
- Windows 发布由 GitHub Actions 构建，正式标签使用 GitHub Secrets 中的 Tauri 私钥和私钥密码；后端只保存并使用公钥验签。预发布标签和手动构建仅生成独立便携客户端 Artifact，不启用正式版更新签名产物。
- Gitee 发布脚本只接受不带预发布标识的正式标签，并在更新正式版 manifest 前复验附件下载、大小、SHA-256、签名、版本递增和增量基线。

## 11. 后续代码变更同步规则

以后每次修改 Go 代码，都必须在同一个工作项和同一个提交中同步更新受影响文档：

1. API、权限、请求/响应字段或错误行为变化：同步 Handler Swagger 注释、docs/API.md、docs/docs.go、docs/swagger.json、docs/swagger.yaml，必要时更新 test.http。
2. 配置、部署、数据库、更新或发布行为变化：同步 README、本文档和 docs/GITEE_RELEASE.md 等相关文档。
3. 业务实现完成、验证阻断、已发现问题或待办状态变化：更新本文档的状态表、验证记录和后续顺序。
4. Web/Tauri 共用 API 变化：同时检查 docs/WEB_STATUS.md、client/API_SYNC.md 和客户端构建约束。
5. 提交前执行与变更范围匹配的测试，并在提交说明或交接记录中分别写明代码、文档、验证和提交状态；代码与对应文档不得无理由拆成不同提交。
